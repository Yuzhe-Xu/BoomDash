# BoomDash 设计思路

> 文档类型：项目总体设计说明
>
> 适用版本：截至 2026-08-29 的 50 个关卡实现
>
> 说明：本文描述当前代码和已确定的玩法约束。`init.md` 是第一关 MVP 的历史实现指南，不能作为当前完整规则的唯一依据。

## 1. 项目定位

BoomDash 是一个竖屏优先的 H5 Canvas 游戏。玩家不直接操控飞船转向，而是在发射前规划炸弹位置，在飞行过程中按时引爆炸弹，用爆炸冲量改变飞船的惯性轨迹，使飞船进入终点区域。

游戏的核心命题可以概括为：

```text
规划炸弹位置 -> 发射飞船 -> 观察惯性轨迹 -> 选择引爆时机
    -> 改变速度和方向 -> 进入任意有效终点 / 失败 -> 重试和优化
```

设计目标不是堆叠操作，而是让玩家从少量、可预测的规则中获得路线规划和时机判断的反馈。每次爆炸都是一次不可逆的速度变化，因此玩家需要同时考虑横向位置、当前速度、剩余飞行时间和目标的进入角度。

## 2. 核心体验设计

### 2.1 间接控制

飞船在空旷太空中保持惯性运动，玩家通过炸弹间接施加冲量：

- 炸弹部署阶段负责空间规划，位置可以自由选择，不做网格吸附和炸弹间距限制。
- 飞行阶段负责时机判断，炸弹只有第一次有效引爆会生效。
- 爆炸方向永远是远离炸弹的位置方向，因此同一枚炸弹的位置同时决定推力方向和强度。
- 爆炸不会自动寻找终点，也不提供直接转向按钮。

这样设计能把“路线”拆成玩家可以理解的两个变量：炸弹放在哪里，以及飞船经过那里时何时引爆。玩家的失败来自决策偏差，而不是隐藏的自动修正。

### 2.2 低规则起步、逐步组合

关卡不在一开始同时引入所有系统，而是按认知负担递增：

1. 第 1-5 关建立炸弹、惯性、目标和世界距离的基础认知。
2. 第 6-20 关使用陨石和规则通道训练横向修正、连续转向和入射角。
3. 第 21-25 关引入星际尘埃，让玩家管理速度损失而不是只躲避禁区。
4. 第 26-30 关引入旋转、往返和循环重入的动态区域。
5. 第 31-34 关引入行星引力，要求玩家理解速度方向和引力井的关系。
6. 第 35-50 关将已有规则组合为多行星、动态障碍、尘埃桥和多路线布局。

新增难度优先来自距离、空间、时机、几何和已有物理规则的组合，不为填充关卡数量随意增加新的物理规则。

### 2.3 失败可解释、成功可复现

生命周期失败原因使用明确枚举：越界、越过顶部、超时、进入陨石或撞上行星。结果页直接展示对应原因，帮助玩家把失败归因到路线决策。

成功路线不写入游戏流程代码。关卡数据只声明出生点、目标、危险区域、尘埃、行星和参数；已覆盖的关卡批次会在测试中以固定步输入回放验证推荐路线。当前各批次的成功路线覆盖程度不同，不能把测试中的一条路线理解为关卡唯一解。

## 3. 总体架构

项目采用 Vite + TypeScript + 原生 Canvas 2D + DOM UI，模块按职责分层：

```text
index.html / main.ts
        |
        v
    GameApp                 应用编排、帧循环、关卡切换、UI 同步
      |       |       \
      |       |        +--> CanvasRenderer / EffectsRenderer / PlanetRenderer
      |       +----------> Camera / PointerInput / KeyboardInput
      v
  GameEvents  ------------> GameSimulation
                              |
                              +--> ShipSimulator / ExplosionSystem
                              +--> LifecycleBounds / GravitySystem
                              +--> GoalGeometry / PlanetMotion
                              v
                          RunState

  LevelCatalog / level*.ts ------> LevelDefinition
  ProgressStore / AudioSystem ----> 持久化和反馈副作用
```

### 3.1 模块职责

| 模块 | 主要职责 | 代表文件 |
| --- | --- | --- |
| 应用编排 | 创建系统、处理帧循环、切换阶段和关卡、同步 DOM | `src/app/GameApp.ts` |
| 事件与阶段 | 定义用户动作和 `planning/flying/paused/success/failed` | `src/app/GameEvents.ts`、`src/app/GamePhase.ts` |
| 固定步模拟 | 排队并应用事件、推进 `RunState`、记录输入、支持回放 | `src/simulation/GameSimulation.ts` |
| 飞船与爆炸 | 发射、冲量、积分、尘埃阻尼、特效寿命、炸弹重装 | `src/simulation/ShipSimulator.ts`、`ExplosionSystem.ts` |
| 生命周期 | 终点、陨石、尘埃、行星和世界边界判定 | `src/simulation/LifecycleBounds.ts` |
| 关卡数据 | 关卡参数、区域、运动定义和目录顺序 | `src/level/LevelDefinition.ts`、`level*.ts` |
| 几何与动态变换 | 规则区域构造、闭合、采样、旋转和时间求值 | `src/level/GoalGeometry.ts` |
| 行星运动 | 静态、圆轨道和线性运动行星的位置求值 | `src/level/PlanetMotion.ts` |
| 输入和相机 | 指针会话、拖动识别、坐标转换、滚动和跟随 | `src/input/PointerInput.ts`、`Camera.ts` |
| Canvas 渲染 | 背景、区域、飞船、炸弹、行星、调试和特效 | `src/rendering/CanvasRenderer.ts` |
| DOM UI | 开始界面、关卡选择、教程、HUD、暂停和结果 | `src/ui/*.ts`、`index.html` |
| 外部副作用 | 最佳成绩、静音状态和 Web Audio 音效 | `src/storage/ProgressStore.ts`、`src/audio/AudioSystem.ts` |

`GameApp` 是编排层，不应把物理规则散落到按钮回调或渲染函数中。UI 操作先转换成 `GameEvent`，再由模拟层检查当前阶段和规则；渲染层读取状态，不负责改变飞船、炸弹或关卡结果。

## 4. 坐标、视口与相机

### 4.1 两套空间的职责

- 逻辑视口固定为 `390 x 844`，用于设备上的显示和 UI 布局。
- 世界宽度固定为 `390`，世界高度由关卡的 `worldHeight` 决定。
- 飞船、炸弹、区域、行星和爆炸特效全部保存为世界坐标。
- CSS 只对整个 `390 x 844` stage 做等比缩放，Canvas 不通过拉伸改变物理比例。
- Canvas 的设备像素比最高取 2，以控制高分辨率设备的绘制成本。

### 4.2 相机规则

`Camera` 只维护纵向 `offsetY`，并始终限制在：

```text
0 <= offsetY <= worldHeight - 844
```

高世界关卡部署时默认显示底部；玩家可以通过鼠标滚轮或触摸拖动浏览地图。飞行时相机根据飞船纵坐标跟随，成功或失败后停留在最后位置。相机变化不修改飞船和炸弹的世界坐标。

指针处理遵循以下顺序：

```text
浏览器 client 坐标
    -> 视口逻辑坐标
    -> 加上 camera.offsetY
    -> 世界坐标事件
```

因此在滚动前后，炸弹的放置、拖动、选择和引爆仍然对应同一个世界位置。

### 4.3 出生点不是起点区域

`LevelDefinition.start` 只提供飞船出生所需的位置和初始数据。当前渲染器不绘制起点轮廓，也不执行起点进入、离开或占领判定。真正参与成功判定的只有 `goals` 中定义的终点区域。

## 5. 物理与生命周期

### 5.1 固定时间步

浏览器使用 `requestAnimationFrame` 驱动画面，模拟使用 `FIXED_DT = 1 / 120` 秒的累积器推进：

```text
frame delta 限制
    -> 累加器
    -> 每满一个固定步就 updateFixed(1/120)
    -> Canvas 渲染插值位置和视觉效果
```

固定步的目的，是让相同关卡、相同参数和相同输入事件序列得到稳定的物理结果，并使路线可以在单元测试中回放。输入事件在模拟边界排队处理，并带有 tick 记录。

### 5.2 事件和固定步的顺序

应用帧在进入固定步循环前会先刷新一次事件队列，`GameSimulation.updateFixed` 的入口也会再次刷新队列。因而 `launch` 或 `detonate` 事件可能在一次固定步积分之前立即改变状态；引爆事件会先计算并应用冲量，然后才进入该步的时间、阻尼、引力和位置积分。当前实现的顺序可概括为：

```text
刷新并应用排队事件
    -> 引爆时立即修改速度
    -> 只在 flying 阶段递增 tick / elapsed
    -> 尘埃阻尼
    -> 行星引力
    -> 速度更新和位置积分
    -> 爆炸效果老化
    -> 用同一 elapsed 评估目标、陨石、行星和生命周期
```

固定步保证状态积分使用固定 `dt`，但浏览器指针事件仍是在渲染帧边界进入队列；因此不能把输入采样时刻描述为完全独立于渲染帧率。

暂停、成功和失败阶段不推进模拟时间，因此动态区域、轨道行星和物理状态被冻结。

### 5.3 炸弹冲量

炸弹到飞船的距离为 `d`，爆炸半径为 `R`，最大冲量为 `I` 时：

```text
direction = normalize(ship.position - bomb.position)
falloff   = clamp(1 - d / R, 0, 1)^2
impulse   = direction * I * falloff
```

超出半径时冲量为零，但炸弹仍被消耗并播放未命中特效。炸弹与飞船重叠时使用 `(0, -1)` 作为方向，避免零向量产生 `NaN`。引力更新本身不调用 `speedCap`；但下一次引爆时，爆炸处理会对“当时已有速度 + 新冲量”的合成结果统一限速，因此不能把引力产生的速度理解为永远不会受到 `speedCap` 影响。

### 5.4 尘埃阻尼

飞船接触一个或多个尘埃区域时，区域的 `dragPerSecond` 相加，并使用指数阻尼：

```text
velocity *= exp(-dragPerSecond * dt)
```

该操作同时缩放速度的两个分量，只降低速度大小，不改变方向。离开尘埃后阻尼立即停止；尘埃本身不会直接导致失败。

### 5.5 行星引力与碰撞

每颗行星由世界坐标中心、半径和 `mu = GM` 定义。引力加速度为：

```text
a = mu * (planet.center - ship.position) / |planet.center - ship.position|^3
```

多颗行星的加速度相加。行星可静止、沿圆轨道运动或按固定线速度运动；模拟和 Canvas 调试几何通过 `planetsAtTime` 获取同一时刻的位置。当前 `DebugOverlay` 的文字引力读数仍基于原始关卡行星位置，属于已知的调试显示限制。

行星碰撞使用飞船半径扩张后的圆，并检查上一位置、当前位置以及两点连线的扫掠结果，避免高速飞行穿透表面。接触行星表面立即失败。

### 5.6 生命周期优先级

当前 `evaluateLifecycle` 的判定顺序是：

```text
行星碰撞 -> 进入任意终点 -> 进入任意陨石 -> 超时
-> 左右/底部越界 -> 越过顶部
```

一个关卡可以有多个终点，进入任意有效终点即可成功。成功时记录实际命中的 `successGoalId`，用于奖励终点归属。

## 6. 关卡与几何设计

### 6.1 数据驱动模型

`LevelDefinition` 集中声明以下内容：

| 数据组 | 内容 |
| --- | --- |
| 身份和空间 | `id`、`name`、`worldHeight`、出生坐标 |
| 目标和风险 | `goals`、`hazards`、`dustRegions`、可选 `planets` |
| 动态行为 | 目标/尘埃的全局运动、陨石的全局或区域级运动、行星实体级运动 |
| 操作参数 | 炸弹上限、爆炸半径、最大冲量、发射速度 |
| 结果参数 | 时间上限、三星/二星分数阈值、飞船半径、速度上限 |

每关是 `src/level/levelN.ts` 中的 TypeScript 数据对象，统一由 `src/level/LevelCatalog.ts` 按稳定顺序导入。目录使用 `findLevel` 和 `nextLevel` 查询，开发阶段所有登记关卡均可直接游玩，不设置解锁逻辑。

### 6.2 共享规则几何

区域由 `CurveRegion` 的 `start`、曲线命令和 `closeEdges` 描述。`closeEdges` 明确声明区域是否借助顶部、右侧、底部或左侧地图边界闭合，避免边界目标产生无限或歧义区域。

当前正式关卡数据遵守五类规则图形：

- 半圆或顶部/角落圆弧区域。
- 一般圆弧或同心圆环扇区。
- 自闭合圆形区域。
- 带圆角的矩形。
- 三角形。

`GoalGeometry` 中的 `topClosedCircularArc`、`cornerQuarterCircle`、`circleRegion`、`roundedRectRegion`、`ringSegmentRegion` 和 `triangleRegion` 负责构造这些区域。渲染使用 `traceGoalRegion`，碰撞和距离计算使用同一结构化区域采样出的 `goalPolygon`，调试层也调用同样的时间求值和路径定义。

实现类型仍保留二次、三次曲线命令的通用能力，主要用于几何表达和历史兼容；这不改变当前新增关卡只使用上述规则图形的约束。

### 6.3 动态区域

区域运动以模拟层的 `elapsed` 为唯一时间来源：

- `angularVelocity` 驱动围绕指定中心的旋转。
- `angleRange.mode = "ping-pong"` 支持端点往返；当前已登记关卡主要使用旋转和 `wrap` 循环重入，尚未使用 `ping-pong`。
- `angleRange.mode = "wrap"` 支持越界后循环重入。
- 陨石区域可以在全局运动下用 `motion: null` 声明静止。
- 动态终点也使用同样机制，绘制、进入判定、调试和奖励 ID 保持同步。

暂停时 `elapsed` 不变，因此动态几何不会在暂停菜单上继续移动。

## 8. UI、反馈与评分

### 8.1 阶段和操作

阶段由 `GamePhase` 统一管理：

```text
planning -> flying -> success / failed
planning <-> paused
flying   <-> paused
```

`CLEAR` 只在部署阶段清空炸弹。`RETRY` 保留位置、重新装填并立即重新发射；`REDEPLOY` 保留位置、重新装填后回到部署阶段，便于微调。暂停时物理时间、飞船和模拟动态全部冻结。

移动端使用 `pointerdown` 尽早响应引爆；炸弹视觉图标之外提供至少 44 CSS 像素的触摸命中范围。部署阶段点击空白处放置炸弹，按住炸弹拖动；高世界关卡的空白拖动则用于相机浏览。关卡选择列表为三列方格，并具有独立的鼠标滚轮和触摸滚动区域。

教程配置在首次引入关键概念的关卡前出现，目前覆盖第一关核心循环、第二关地图浏览、第四关评分、第六关陨石、第九关奖励、第二十一关尘埃和第三十一关引力，并提供循环动图。当前没有持久化的“已读教程”标记，重新进入对应关卡时仍会再次显示。

### 8.2 评分

基础分满分为 10000，时间权重 0.6，炸弹权重 0.4：

```text
timeFactor = clamp((timeLimit - elapsed) / timeLimit, 0, 1)
bombFactor = clamp((maxBombs - usedBombs) / maxBombs, 0, 1)
baseScore  = round(10000 * (0.6 * timeFactor + 0.4 * bombFactor))
score      = baseScore + max(0, round(bonusScore))
```

当前奖励终点出现在第 9、14、30 关。结果页显示本次分数、时间、炸弹数、可选 BONUS、BEST 和星级；成功时星星按顺序点亮。星级由各关 `star3Score` / `star2Score` 判定，失败不记分，星级不参与解锁。

### 8.3 视觉语言

视觉主题是深色、克制的霓虹太空控制台：

- 深黑背景提供低干扰空间。
- 青色表示信息和交互，洋红色表示选中，荧光绿色表示目标和成功。
- 红色表示陨石危险，灰色表示尘埃，棕褐色表示岩质行星，金色 `+` 表示奖励终点。
- `Orbitron` 用于标题和主要状态，`Share Tech Mono` 用于 HUD、按钮和数据。
- 发射闪光、尾迹、爆炸环、粒子和星星点亮只承担反馈，不改变物理结果。

字体以本地 WOFF2 形式随生产包发布，避免依赖 Google Fonts 网络请求。

## 9. 存档、发布与质量策略

`ProgressStore` 使用 `boomdash.<levelId>` 保存每关的最低最佳时间、最高最佳分数和静音状态。关卡选择由目录实时生成，读取保存的 `bestScore` 推导星级。

质量验证分三层：

1. **系统单元测试**：覆盖向量、相机、阶段、爆炸、几何、生命周期、尘埃、引力、行星自转、评分、教程和存档。
2. **关卡固定步测试**：按批次验证目录追加顺序、结构化布局、直飞失败、部分推荐炸弹路线成功和奖励终点归属。当前第 35 关没有成功路线断言，第 36-39 关只有第 37 关有成功路线，第 44-48 关只有第 44 关有成功路线，第 49-50 关各有一条成功路线。

## 10. 设计边界

当前方案有意不引入以下系统：

- 直接操纵飞船方向、自动寻路或自动瞄准。
- 起点区域、墙体反弹、风场、敌人和路线吸附。
- 炸弹导火索、连锁爆炸、多段冲击波和炸弹间碰撞。
- 账号、联网、排行榜和服务端存档。
- 外部关卡编辑器或运行时 JSON 加载；当前关卡是 TypeScript 常量。

这些边界保证核心物理和关卡数据保持可读、可测试、可回放。后续扩展应优先复用现有事件、固定步和几何数据结构，只有在明确玩法需求和测试覆盖同时成立时才增加新规则。
